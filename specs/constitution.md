# ECHO 專案憲章 (Constitution)

> 本文件定義專案不可妥協的原則。所有 spec / plan / tasks 與程式碼都必須遵守；若需違反，須先修改本文件並記錄理由。

## 開發流程：Spec-Driven Development

1. **規格先行**：任何功能先寫進 `specs/<編號>-<名稱>/spec.md`（做什麼、為什麼），經確認後才寫 `plan.md`（怎麼做），再拆成 `tasks.md`（逐步執行）。
2. **可追溯**：每個任務 (T###) 必須對應至少一條功能需求 (FR-###) 或驗收條件 (AC)；每條 FR 必須有對應的任務與驗證方式。
3. **規格是唯一真相**：實作中發現規格不合理 → 先改 spec，再改程式碼，不得只改程式碼。
4. **小步交付**：每個任務完成後可獨立驗證（測試通過或可手動驗收），再進入下一個。

## 技術原則

- **安全靠資料庫，不靠前端**：前端金鑰是公開的，所有權限一律以 Supabase RLS + 欄位權限 + trigger 強制執行。前端隱藏按鈕只是 UX，不是安全機制。
- **最小可行**：先完成 P1 使用者故事再碰 P2/P3；不為「未來可能」預先抽象。
- **型別安全**：TypeScript strict；資料庫型別由 `supabase gen types` 產生，不手寫。前端使用的領域模型（`src/types/models.ts`）可以手寫，DB 型別與模型之間的轉換只在 `src/services/` 內進行。
  - 理由（2026-11-02）：採 UI 先行（spec D8），畫面需要在資料庫建立前就有穩定的型別；轉換集中在 services，日後換成真實後端時元件與 store 不必改。
- **資料存取集中**：元件不直接呼叫 `supabase`，一律經 `src/services/*` → `src/stores/*`。假資料實作（`src/services/mock/`）與 Supabase 實作提供同一組介面。
- **零成本**：只使用 Supabase 與 GitHub 的免費方案。需要付費才能啟用的功能一律不做，列入 spec 的「需付費、暫不做」清單（001 spec §7.1）。
  - 理由（2026-11-02）：專案負責人決定只用免費方案。
- **測試**：RLS 政策必須有 pgTAP 測試；商業邏輯（排序、篩選、格式化）必須有 Vitest 單元測試。

## 使用者體驗原則

- **行動優先**：主要情境是會友在座位上用手機掃碼，須在小螢幕單手可操作。
- **零門檻**：會友不需註冊、不需安裝 App，掃碼後 3 秒內可開始留言。
- **長者友善**：字體至少 16px、按鈕觸控區 ≥ 44px、對比符合 WCAG AA。
- **介面語言**：繁體中文（台灣用語）。
- **尊重隱私**：會友預設匿名；不收集姓名、電話、Email 等個資。
